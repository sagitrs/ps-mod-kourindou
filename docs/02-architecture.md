# 架构与存档设计

[产品要求](01-product-design.md) · [证据与风险](07-evidence.md) · [决策表](03-decisions.md)

本文是拟议实现结构，不是已经存在的API或已运行代码。目标游戏构建、程序集、SDK和运行框架必须先由V1-02验证，再锁定具体类型与方法。

## 1. 一套状态与调度，多个内部模块

| 层 | 职责 | 不应该做的事 |
|---|---|---|
| 内容目录 | 角色、城区映射、对白、立绘、背景、帮助/CG定义 | 存放玩家好感或复制游戏资产 |
| 纯规则层 | 上限、门槛、权限、加权抽样、日程去重 | 直接读Unity对象或本机文件 |
| 游戏适配层 | 读真实城区声望/买店/日期，接顾客与交易事件，调整表现 | 把猜测的方法名当成稳定官方API |
| 状态层 | 按局数据、schema版本、恢复/迁移、身份关联 | 用全局配置混放所有存档进度 |
| 表现层 | 角色面板、夜间入口、背景、CG与错误提示 | 为换图重建库存/店铺或盖住交互区域 |
| 生命周期层 | 初始化、加载、事件订阅、停用与资源清理 | 在主菜单阶段读取尚不存在的游戏经理/存档 |

顾客选择只允许一个核心流程负责：合格候选 → 已批准日程规则 → 剩余自然客流抽样 → 创建普通交易顾客 → 到场/成交记录。地区加权和每日保底不能各挂一套互不知情的生成器。

## 2. 游戏适配合同

下面是需要验证的“能力”，不是声称游戏已存在同名方法：

- 识别下/中/上城区的稳定内部身份与声望值；确认100在实际量纲中的含义，不自行归一化改门槛。
- 读取原生买店持久状态；同时识别新购店事件和已买店旧档。
- 读取游戏日和营业状态；处理一日内重复开门/关门，不能把每次开门当成新一天。
- 新建正常买家/卖家并带上可追踪的东方身份；正确准备需求、资金和货品。
- 区分生成、入队、到场、成交、取消、剧情来访；确认交易成功事件来自实际流程。
- 将店面背景放到正确对象/图层；保留柜台、光照、交互和外出返回行为。
- 通过合适原生入口执行钱款变化与三项已选帮助效果。
- 识别新局命名时机，避免默认店名覆盖玩家选择。

优先采用原生ModHook/ModHelper；没有覆盖时，对**游戏代码**做必要的小范围适配。白天店面背景不是夜间地点的`backgroundKey`接口。新顾客头像没有稳定注册API，社区立绘框架只换既有图，不能直接证明独立新角色可用。

每个适配点记录游戏构建、程序集摘要、真实签名、触发时序与验证记录。目标不匹配时明确禁用受影响功能或停止Mod启动，不继续写存档后假报正常；降级范围必须让玩家看得见。禁止绕过游戏扫描、信任或权限声明。

## 3. 角色身份

建议内部使用不会随中文名变化的ID，例如`alice`、`marisa`、`sakuya`；完整Mod命名空间待定，不把示意ID当作已发布协议。

一个东方角色ID与多个临时买卖顾客实例关联。角色好感、CG和来访偏好归角色；交易对象还需保留本体类型/功能身份。`SetClientSource`之类的Mod来源标记不等于唯一角色ID。

不得通过“看头像/看名字”推断好感归属，不用全局替换同一原生头像键来冒充三个独立人物。不得因移除内容包而把一个人的旧进度转给新角色。

最终全NPC随机替换需要增加映射策略，但V1三人固定，不实现随机映射。最终若选择每局固定映射，需要保存结果/版本而不仅是一个随角色池变化会产生不同结果的随机种子；该决定留到后续。

## 4. 状态和保存

建议的逻辑状态如下，字段不是已存在的游戏成员：

| 状态 | 所属范围 | 要求 |
|---|---|---|
| schemaVersion、内容版本 | 每局 | 明确迁移，不猜未来格式 |
| currentRegionId、地区资格/选择记录 | 每局 | 对应原城区资格，换背景不造新店 |
| affection[characterId] | 每局 | 当前值、必要的已批准增长记账 |
| visitMode[characterId] | 每局 | 自然/买家/卖家；生效日规则另定 |
| schedule与到场/成交记录 | 当前游戏日/每局 | 区分计划与事实，读档与多次开门不重复 |
| helpUsage与效果状态 | 每局/游戏日 | 防重复支付、重复效果及跨档混用 |
| CG解锁/待播放/已播放记录 | 每局为建议 | 不在播放失败时丢失解锁；跨档收藏另定 |

通过原生按局ModData保存小型结构数据；图片、完整内容定义和运行时Unity对象不写进去。只有在存档可用后读取，随游戏的正常保存周期落盘，点击成功不等于立即持久化。

只有游戏经理/资源已就绪，才重建UI、背景或访客关联。游戏自动存档与睡眠钩子的准确先后顺序需要实测：只保存需要跨保存点持续的状态，瞬时入队对象不能未经核实就跨存档复制。

坏数据、未知schema或缺包应提供诊断并保留原始数据，不静默清空、不把高版本数据写成低版本空状态。迁移应有可恢复副本/测试样本及独立验证；实际文件操作使用游戏许可入口。

## 5. 钱款与帮助效果

先检查资格、可用性、余额、次数和效果前提；处理期间阻止重入；再执行经该效果验证的扣费、应用和记账流程。部分失败的恢复方案由具体效果决定，例如撤销临时增益或返还未成功消费的款项。

不能先给出不可撤回物品再在异常后无条件退款，也不能扣费失败仍给效果。帮助记录与本体钱款需在同一个实际游戏保存边界下复现一致。读取较早存档导致钱款和进度一起回退是正常单机行为，不实现联网防SL。

## 6. 停用、兼容与资源

- 用原生可保存的普通顾客载体和ModData身份关联是优先探索方向；不能让保存内容必须加载本Mod自定义CLR类型才能反序列化。
- 必须实测“保存 → 关闭游戏 → 不加载Mod → 原版读档”，不是只在运行中调一次OnDisable。原生存档里出现Mod头像键、顾客或效果时也要测试。
- 取消本Mod订阅、移除自身UI、释放自身资源，撤销可逆表现。恢复背景前确认对象仍由自己控制，避免覆盖其他Mod后来的修改。
- 不清除自己的持久进度以模拟卸载成功；同时不承诺自动撤销已完成交易、钱款或原剧情。
- 同类立绘/客流Mod可能冲突，明确兼容声明和优先级，不通过高优先级补丁强行覆盖别人而称“全兼容”。
- CG按需加载并释放，防止全量高清纹理常驻。不会因为开发服务器内存大就提高玩家最低配置。

## 7. 构建与分发边界

优先Linux构建纯逻辑及托管DLL、Windows正版客户端验收。`netstandard2.1`与`net48`均见于参考项目，不能未经实际程序集核对就任选其一。SDK版本不代表游戏支持同版本运行时API。

游戏引用应在仓外受控只读目录，构建显式接收路径；不提交/分发游戏DLL、游戏自带Harmony或游戏资源，不让CI公开缓存它们。没有私有引用时，逻辑测试可以运行，但游戏集成构建必须明确报告缺输入，不能用假类型桩冒充成功。

模块化不等于建立通用插件平台。V1只实现三角色需要的最小接口和数据结构，后续扩包格式要有真实用例再固定。

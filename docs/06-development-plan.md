# 开发计划

[产品设计](01-product-design.md) · [决策](03-decisions.md) · [Issue目录](../planning/README.md)

计划规定顺序与交付条件，不承诺尚无依据的工时/日期。当前没有排班、自动派工或实施授权扩大；后续实施按本仓有效审阅规则进行。

已建立原生层级：[主票 #1](https://github.com/sagitrs/ps-mod-kourindou/issues/1) → [V1总票 #3](https://github.com/sagitrs/ps-mod-kourindou/issues/3) → V1-01至V1-12（#4—#15）。编号和依赖见[规划目录](../planning/README.md)；F三项仍未开票。设计PR合入、开票、开始实现及产品验收是不同状态。

## 1. 分阶段交付

| 阶段 | 任务 | 出口 | 不应冒充 |
|---|---|---|---|
| S0：确认设计/输入 | V1-01，准备D10/D11 | 对相关规则有明确选择；有合法游戏引用与测试入口计划 | 文档齐不等于所有决策已定 |
| S1：先证高风险 | V1-02 | 最小原型用真实程序集构建并在真实游戏验证身份/立绘、买卖、背景、声望/买店/日期、存档兼容关键点；锁工具版本 | 只编译/显示窗口不代表新角色可行 |
| S2：基础与角色 | V1-03、V1-04；V1-10并行准备 | 可维护工程、状态/事件接入，三人独立身份和主角/店名；原NPC不被替换 | 只换脸不算新增三人 |
| S3：完整玩法 | V1-05至V1-09 | 好感/买店、搬迁、三人夜援、每日来访、CG形成完整循环 | 不能只有菜单或只在桩里运行 |
| S4：内容/回归 | V1-10、V1-11 | 正式资源齐、跨功能游戏内回归、存档/禁用/性能/安全证据 | 占位图不算正式内容，未测不算通过 |
| S5：候选包与交接 | V1-12 | 固定版本候选包、安装/备份/卸载说明、验收记录与已知限制 | 包已打好不等于公开发布或终版完成 |

高风险原型可以先用一个角色、占位图和可丢弃测试档，但V1最终仍是三城区三人及全部既定玩法。原型发现不可行时，先提交准确限制与替代方案，由用户决定，不自行改成纯换皮或删除保底要求。

## 2. 任务依赖

机读关系见[Issue索引](../planning/issues.json)，人工导航见[目录](../planning/README.md)。依赖表示需要上游的接口/证据，不必一律等到其远端Issue关闭才协作；设计未定不能假作已定。

主要顺序：

                                               ↓
                                          V1-04 三角色
                                         ↙           ↘
                            V1-05 好感/买店       V1-06 地区
                             ↓       ↓              ↘
                       V1-07夜援   V1-09 CG       V1-08每日来访

V1-08同时依赖V1-05和V1-06。所有功能任务自带测试；V1-11负责组合验证，不承接被前面省掉的验证义务。

## 3. 每项任务的共同完成条件

- 需求和已确认D项可追踪，实际变更不超过当前范围。
- 产品代码、配置、测试和使用说明一起提交；具体PR流程采用目标仓有效规则。
- 作者自测结果与真实对象可核；按目标仓安排独立审阅/验收，不由作者自称需求已验收。
- 环境不足、未覆盖和产品失败如实分开；不以CI绿色替代游戏内测试。
- 未解决的关键缺陷不靠关闭按钮消失。验收、合入、Issue结算与公开发布分开。

V1-12只准备交付候选包和材料；Steam Workshop或其他公开渠道的上传需要另外确认渠道、权限、许可与发布意愿。

## 4. 后续到最终目标

长期总票GOAL下同时保留V1和三个后续方向：

1. **F-01：全NPC随机东方化。** 完整盘点NPC与剧情功能，确认随机规则及角色池，再拆设计、替换器、保存迁移、内容和兼容任务。最终覆盖所有NPC，而非永久只覆盖普通顾客。
2. **F-02：赛博设定清理。** 盘点并替换相关人物/组织、对白、物品、场景、界面等；明确每项保留的功能与新的东方表现，不只做关键词替换。
3. **F-03：最终版本组合验收。** 证明全NPC映射、世界观替换、原经营/新养成可共同运行，给出升级与长期维护边界。

这些是待分解的长期任务，不是现在就能执行的精细施工票，不虚构最终角色表、版本号或日期。建议V1验收后再组织下一轮，但这只是排期建议，不产生无人确认的自动启动。

## 5. 风险与应对

| 风险 | 首先应做的事 |
|---|---|
| 最新文档API不在用户构建中 | V1-02用真实程序集/游戏核对，不盲抄示例 |
| 新角色无法稳定接入、立绘共享键串人 | 在扩美术前验证独立身份与正常买卖 |
| 白天背景与夜间接口混淆 | 单独验证店面图层、交互、外出返回 |
| 日程/交易事件误判导致刷好感或漏保底 | 区分计划、到场、成交，测试重复开门和取消交易 |
| 卸载后保存了无法加载的自定义顾客类型 | 先验证原版无Mod载入，必要时回到载体/状态方案设计 |
| CG和帮助内容空缺 | D03/D12分别明确玩法和资源，别把占位原型算完成 |
| 官方安全规则继续调整 | 避免将要退出的能力；锁目标版本，升级重新扫描和回归 |
| 最终大改挤占首版 | V1和F任务分账，接口仅做必要预留 |

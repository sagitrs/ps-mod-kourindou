## 1. 入仓前

1. 确认仓主、平台/地址、可见性、授权账号、采用的贡献/审阅规则及需求验收安排；不从机器人名或历史权限推定有权创建仓。
2. 对设计和D决策做一轮审阅。允许待定项以明确阻塞记录入仓，但不能将未定规则写成已通过规格。
3. 选择代码/文档许可证，另外核美术和其他第三方权利。没有许可证不等于默认沿用参考框架MIT。
4. 检查目标仓真实存在的贡献说明、目录结构和已有Issue，避免重复开票/覆盖已有工作。无载体时记录缺口，不伪造不存在的规范路径。
5. 仅导入本包的`README.md`、`docs/`、`planning/`等文档内容；本地取证、凭据、安装目录、游戏DLL和私人存档不在其中。

## 2. 文档提交

在获准分支提交文档，通过目标仓PR/评审流程。仓内Markdown相对链接以本包根目录为基准，若放入子目录，需要一起调整导航。

本仓没有Mod源码、游戏构建/运行入口或CI配置。已有的`tools/docs/`仅为可运行文档检查及自测，不能冒充游戏测试。后续工程票负责产品构建与CI，不能展示不存在的构建命令或绿色徽章。

## 3. Issue结构

共17项规划：GOAL、V1和12项V1开发任务对应14张真实Issue，索引含其编号/URL；其余3项后续任务保持未发布。规划ID不是平台Issue号。原生父子关系已通过GitHub的父票接口及两层子票列表回读，不以Markdown列表冒充。

```text
GOAL #1 最终目标
└── V1 #3 首版本交付
    └── V1-01 … V1-12（#4—#15）

仍属GOAL范围、尚未创建：
F-01 全NPC随机东方化
F-02 赛博设定清理
F-03 最终版本组合验收
```

每份正文含目标、范围/非目标、依赖、待定决策、交付物及验收条件。标签只是建议：需求用`requirement`，总票可加`umbrella`；实际标签/状态族按目标仓规则处理，不创建半套状态标签，也不冒充已有label配置。没有分配实际负责人。

## 4. 发布时的安全顺序

1. 先读取目标仓现状并按规划ID/稳定标记查重。
2. GOAL、V1及V1-01至V1-12已存在，不再创建。获得后续开票授权后，先核现状，再创建获准的其余票；每次成功立即记录远端ID/URL、正文摘要与返回结果。
3. 请求结果未知时先查回现状，不盲目再次POST。正文中的稳定标记用于辅助对账，不是自动防重事务。
4. 将本地文档相对链接换成目标仓**固定提交版本**的可访问链接；将父票/依赖的规划ID换成真实Issue链接。不要原样粘贴以为`../../docs/`在Issue页面也会正确解析。
5. 平台支持原生子Issue时建立层级，并逐个读回确认；不支持则使用明确的父子链接和任务列表，不能声称已建原生关系。
6. 更新本地规划ID→远端ID/URL对照，再读回标题、正文、父子关系、标签和依赖。发布状态只有实际确认后才更改。

不提供一键自动建票脚本，避免把草稿里的未决事项和未授权目标自动发布。创建Issue不是派工、完成、批准或关票，不能因子票创建或关闭就自动结算父目标。

## 5. 不能随文档迁移的内容

游戏程序集/资源、真实存档、Steam登录、API令牌、密码、私有SSH密钥、授权管理链接及其他任务目录均不进入仓库。合法游戏引用在后续构建环境按最小范围提供；公开CI不能顺带缓存或上传。

代码合入、游戏实测、验收、候选包交付与公开发布分别确认。V1-12准备的是包与交接，不自行授予Steam Workshop上传或官方发布权。
